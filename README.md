# Lulio: baby tracker

Приложение для учёта сна, кормлений и других событий. Дневник работает локально без интернета. Для обмена между телефонами родителей можно выбрать **ручную синхронизацию через Яндекс Диск** или существующую автоматическую синхронизацию Supabase. Одновременно включить оба способа нельзя.

Версия **1.2.0** добавляет редактирование даты и времени сохранённых записей, включая начало и окончание сна. Статус публикации APK и PWA проверяется отдельно по процедурам в `DEPLOY.md`.

Версия **1.1.0**: приложение переименовано в **Lulio**; заголовок приложения — **Lulio: baby tracker**. Репозиторий: [Chernikovmax/lulio-baby-tracker](https://github.com/Chernikovmax/lulio-baby-tracker). Идентификатор Android `io.ionic.starter`, ключи локального хранения и форматы синхронизации сохранены для совместимости с существующими дневниками.

В списке событий дата и время отделены от описания отступом 12 px. Дата не переносится, а длинные названия и заметки переносятся внутри карточки на узких экранах.

Возраст в заголовке дневника считается от даты рождения на выбранный день; ПДР на него не влияет. В режиме «Сегодня» дата и возраст автоматически обновляются после полуночи и при возвращении из фона, даже если приложение не перезапускали несколько дней. Вручную выбранный прошлый день сохраняется; кнопка «Сегодня» возвращает текущую дату и её автоматическое обновление.

При ручном вводе грудного кормления укажите начало и целые минуты у каждой груди. Окончание вычисляется автоматически как начало плюс сумма этих минут, без пауз; отдельно выбирать его не нужно. Рассчитанное окончание не должно быть в будущем. Текущий таймер ручная запись не изменяет.

Перед запуском таймера сна или грудного кормления можно прокрутить колесо «Началось минут назад» от **0 до 60**. По умолчанию выбрано **0** — запуск сейчас; при выборе **10** отсчёт начинается с **10:00** и продолжается. Для кормления прошедшее время относится к груди, выбранной при запуске; паузы и смена груди работают как обычно. Прошлое начало сохраняется при перезапуске приложения и в завершённой записи. Выбор минут доступен только до запуска и сбрасывается в 0 для следующего таймера.

В истории нажмите **карандаш** у записи, чтобы исправить её дату и время. У сна можно изменить начало и окончание, в том числе на разных датах: длительность, итоги и интервалы бодрствования пересчитываются автоматически. У событий без окончания меняется время события. Правка сохраняет исходный ID, заметки и остальные данные, не создаёт дубль и участвует в обычной синхронизации. Окончание должно быть позже начала; время в будущем не допускается. Для грудного кормления длительности у каждой груди сохраняются, поэтому новый интервал должен вмещать их сумму. **«Закрыть»** отменяет несохранённые изменения.

## iPhone: установка PWA

**Основной адрес Lulio: baby tracker:** [https://lulio.website.yandexcloud.net/](https://lulio.website.yandexcloud.net/). Это PWA с отдельной иконкой, не приложение из App Store. Версия **1.1.0**, production-сборка от **22 октября 2026, 19:08 UTC**, опубликована **22 октября, 19:31 UTC**. В этой сборке ошибки запросов Яндекс Диска различают этап операции и HTTP-статус; расшифровка — в разделе «Состояния и ошибки». Хостинг — российский Yandex Object Storage без платного домена/CDN/gateway. Риск расходов сверх бесплатных объёмов принят; жёсткого ограничения расходов это не создаёт. Техническая инструкция и точные результаты: [DEPLOY.md](DEPLOY.md).

Настроено уведомление владельцу о достижении **10 ₽ расходов за месяц** (`lulio-monthly-cost-alert`, активно до 31 октября 2027 года); оно охватывает и новый бакет. Это только уведомление, не ограничение списаний и не автоматическое отключение сайта. Жёсткий месячный лимит 50 ₽ не установлен: бюджеты Yandex Cloud не останавливают потребление. Платный домен `.ru` не зарегистрирован; основной адрес использует бесплатное имя бакета `lulio`.

1. Откройте **[Lulio в Safari](https://lulio.website.yandexcloud.net/)**, не во встроенном браузере мессенджера. Рекомендуется актуальная iOS; минимальная цель текущей сборки — Safari/iOS 17. Более старые версии не поддерживаются этой конфигурацией Angular.
2. Нажмите **«Поделиться» → «На экран Домой» → «Добавить»**. Если Safari предлагает «Открывать как веб-приложение», оставьте включённым.
3. Запустите приложение с новой иконки **с интернетом**. Первая загрузка скачивает оболочку, все экраны и иконки. До завершения установки service worker офлайн-запуск не гарантирован.
4. Проверьте установку: закройте приложение, включите авиарежим и откройте иконку снова. Должны открываться дневник, статистика и профиль, сохраняться новые записи. Первый в жизни запуск без сети невозможен.

На настоящем iPhone отдельно проверьте иконку, отсутствие панелей Safari в standalone, вырез экрана/индикатор «Домой», портретную и альбомную ориентацию, ввод текста с экранной клавиатурой, закрытие модальных окон и возврат после блокировки. Автоматический WebKit smoke не заменяет эту проверку.

### Прежний адрес отключён

По просьбе владельца публикация `lulio-baby-tracker.website.yandexcloud.net` отключена: удалена настройка веб-сайта, закрыто анонимное чтение и удалены все 62 файла старой публикации. Старый бакет пуст; архивы сборок для отката сохранены только локально. Используйте **https://lulio.website.yandexcloud.net/** — рабочая публикация не изменялась.

Ранее установленная старая PWA может ещё открываться из своего офлайн-кеша. Её кеш и локальный дневник не очищались и автоматически на новый адрес не переносятся.

Если у вас уже есть JSON-копия дневника, импортируйте её на новом адресе через **Профиль → Импортировать из JSON**. Импорт полностью заменяет местную историю; сначала сохраните отдельную копию существующих данных. На iPhone добавьте новый адрес на экран «Домой» и проверьте данные именно в новой установленной PWA.


### Офлайн, таймеры и обновления

- Без сети доступны локальный дневник, профиль, таймеры, статистика и JSON-резервирование. Синхронизации нужен интернет.
- Таймер сохраняет дату старта и накопленное время. Когда iOS замораживает или выгружает приложение, код не продолжает работать в фоне; при возвращении длительность пересчитывается по времени старта. Не меняйте часы устройства во время измерения.
- PWA **не реализует Web Push, нативные уведомления или фоновый обмен**. Android-уведомления из APK не появляются в веб-версии.
- При готовом обновлении сверху появляется предложение перезагрузить приложение. Сначала сохраните открытые формы, затем нажмите **«Перезагрузить»**. Уже поставленные в очередь записи дневника сохраняются перед перезагрузкой; несохранённый текст формы не сохраняется автоматически.
- Можно вручную нажать **Профиль → Проверить обновление**. Пока новая версия полностью не скачана, service worker сохраняет текущую. Обновление применяется целой перезагрузкой, без переключения отдельных бандлов в работающей вкладке.
- Обновление не меняет ключ и формат локального дневника. OAuth-сессия Яндекса в веб-версии живёт только в памяти и после перезагрузки теряется — войдите заново.
- Не очищайте «Данные сайтов» и не переустанавливайте PWA для получения обновления: это может удалить дневник. Смена адреса сайта также создаёт другое хранилище.

### Хранилище и резервные копии

В браузере Capacitor Preferences использует `localStorage`. Это не облачная база, не шифрованный сейф и не бессрочное хранилище. Система, пользователь, приватный режим, недостаток места или политика Safari могут удалить/ограничить данные. Кеш оболочки service worker **не является резервной копией дневника**.

- В **Профиль** можно запросить постоянное хранение. Поддержка и решение зависят от браузера; даже положительный ответ не заменяет копии.
- Регулярно нажимайте **Профиль → Скачать резервную копию**, особенно перед обновлением iOS, сменой устройства, адреса сайта или удалением приложения. На iPhone проверьте файл в «Файлах»/«Загрузках» и сохраните его в личное защищённое место.
- Копия содержит личные записи без шифрования приложения. Не загружайте её в публичный бакет хостинга, репозиторий или публичные ссылки.
- Safari, другая программа просмотра и установленная PWA могут иметь разные хранилища. Если дневник из Safari не появился под иконкой, экспортируйте JSON в Safari и импортируйте в PWA. **Импорт полностью заменяет локальную историю**; перед ним сохраните отдельную копию текущих данных.
- Не редактируйте один локальный дневник одновременно в нескольких вкладках. Для двух телефонов нужен отдельный способ синхронизации; публикация PWA сама по себе данные между супругами не передаёт.

### Что проверено, а что нет

На коротком публичном HTTPS-адресе в отдельном Chromium-профиле проверены manifest/icons и installability без ошибок, активация и управление через service worker, прямой вход на все четыре экрана, офлайн-перезагрузка и открытие после полного перезапуска браузера. Синтетические профиль и запись экспортированы с прежнего адреса и импортированы через интерфейс нового; после офлайн-перезапуска они сохранились, исходный дневник на прежнем адресе не изменился. Таймер, JSON-экспорт и мобильная раскладка с основными кнопками около 79 px дополнительно проверялись на прежнем адресе для тех же файлов приложения.

Для этой сборки последовательно прошли TypeScript, production build и **53 теста в 12 файлах**. В новом бакете **62 production-объекта**; они побайтно совпадают с проверенным артефактом, MIME/cache-control проверены, отсутствующий JS возвращает настоящий 404, список и настройки бакета приватны. На прежнем адресе проверено обновление на вторую публичную SW-версию без потери дневника, профиля или таймера; во второй сборке изменился только timestamp SW-манифеста, не JS-бандлы. Перенос адреса не создавал новую версию приложения. Артефакт: `dist/lulio-pwa-20261022T142210Z.zip`; прежняя публикация и архивы сохранены для rollback.

Не подтверждены: установка/жизненный цикл на физическом iPhone, реальная экранная клавиатура, очистка хранилища самой iOS, доступность из российских сетей, публичное обновление с изменёнными JS-бандлами и реальная синхронизация Яндекс Диска. Ранее локально проверенные мобильный WebKit и обновление с другим main-бандлом не заменяют эти проверки.

Для Яндекс Диска реальные запросы без действующей сессии из тестового браузера позволили прочитать OAuth HTTP 400 и Disk HTTP 401 через CORS. Это доказывает лишь доступность этих ответов с локального origin, **не успешный OAuth/PKCE, загрузку файлов или обмен двух родителей**. CORS и доступность нужно повторить с конечного HTTPS-адреса и реальными аккаунтами; токен не переносится в постоянное браузерное хранилище. Существующий Supabase также требует отдельно настроенного сервера и проверки с двух устройств; российская доступность здесь не подтверждена.


## Яндекс Диск: как пользоваться вдвоём

При передаче ребёнка:

1. Передающий родитель открывает **Профиль → Яндекс Диск · ручной обмен**, нажимает **«Синхронизировать»** и ждёт успешного завершения.
2. Принимающий родитель после этого нажимает **«Синхронизировать»** на своём телефоне.
3. Принимающий родитель проверяет историю и активный таймер. Если он тоже отправил свои новые события, первый родитель получит их при следующем нажатии.

Кнопка работает в обе стороны: получает доступные семейные изменения и отправляет локальные. Интернет нужен только для обмена. Записи, которые первый телефон ещё не отправил, на втором появиться не могут.

**Это не обмен в реальном времени.** Если оба родителя нажали одновременно, после завершения повторите синхронизацию: пакет другого телефона мог появиться уже после чтения списка файлов. Время последнего успешного обмена не означает, что другой родитель отправил все свои записи.

## Первоначальная настройка

### 1. Подготовить общую папку

1. На компьютере откройте [Яндекс Диск](https://disk.yandex.ru/) в браузере.
2. Создайте отдельную семейную папку, например **Baby Tracker**. Для тарифа Яндекс 360 «Для семьи»: **Создать → Семейную папку**.
3. У обоих родителей должно быть право **«Редактирование»**, не только «Просмотр».
4. Убедитесь, что папка видна в аккаунте каждого родителя. Для обычной общей папки приглашение нужно принять; для участников семейной группы Яндекс описывает автоматическое принятие приглашения в семейную папку.
5. Не создавайте публичную ссылку. Она для синхронизации не нужна.

Каждый входит **в собственный Яндекс ID**. Не нужно передавать друг другу пароль или использовать один аккаунт на двух телефонах. Общая папка может иметь разное имя и путь у разных участников — выбирайте её отдельно на каждом телефоне.

Справка: [семейные папки](https://yandex.ru/support/yandex-360/customers/disk/web/ru/share/shared-folders-family), [права участников общей папки](https://yandex.ru/support/yandex-360/customers/disk/web/ru/share/shared-folders-to-me).

### 2. Зарегистрировать OAuth-приложение Яндекса

Этот шаг выполняется один раз владельцем проекта, до подключения телефонов.

1. Откройте [Яндекс OAuth](https://oauth.yandex.ru/).
2. Создайте приложение **«Для авторизации пользователей»**, чтобы каждый родитель мог выдать разрешение со своего аккаунта. Тип **«Для доступа к API или отладки»** в текущей документации описан как предназначенный только для данных самого разработчика; не выбирайте его для одного общего ClientID двух пользователей.
3. Укажите название приложения и контактную почту, настройте платформу **«Веб-сервисы»** для браузерного получения одноразового кода.
4. В **Redirect URI** укажите точно:

   ```text
   https://oauth.yandex.ru/verification_code
   ```

5. Добавьте необходимые разрешения Диска:

   ```text
   cloud_api:disk.read
   cloud_api:disk.write
   ```

6. Сохраните приложение и скопируйте **ClientID**: строку из 32 шестнадцатеричных символов. Один ClientID можно указать на обоих телефонах, но каждый родитель авторизуется отдельно.

**Client Secret не копируйте в мобильное приложение, README или исходники.** Приложение использует Authorization Code + PKCE S256 и не запрашивает секрет клиента. Разрешения профиля, почты и контактов для этой функции не нужны. Яндекс может показывать предупреждение для неверифицированного сервиса; настройка и доступность OAuth-приложения зависят от правил Яндекса.

Важно: `disk.read` и `disk.write` дают приложению доступ **ко всему Диску**, хотя реализация файлового обмена работает только с выбранной папкой. Более узкое право `cloud_api:disk.app_folder` не даёт доступа к выбранной семейной папке и здесь не подходит.

Документация: [типы OAuth-приложений](https://yandex.ru/dev/id/doc/ru/register-client), [регистрация пользовательского приложения](https://yandex.ru/dev/id/doc/ru/register-auth), [одноразовый код и PKCE](https://yandex.ru/dev/id/doc/ru/codes/screen-code), [разрешения API Диска](https://yandex.ru/dev/disk-api/doc/ru/concepts/quickstart).

### 3. Подключить первый телефон

1. Установите актуальную нативную сборку приложения. После добавления плагинов нужна новая сборка, обновления только веб-файлов недостаточно.
2. Откройте вкладку **«Профиль»**. Если включён Supabase, снимите его флажок и нажмите **«Сохранить настройки синхронизации»**.
3. В разделе **«Яндекс Диск · ручной обмен»** вставьте **ClientID**.
4. Нажмите **«Войти в Яндекс»**. В открывшемся браузере выберите свой аккаунт и разрешите чтение и запись Диска.
5. Яндекс покажет **одноразовый код подтверждения**. Скопируйте его целиком, включая латинские буквы и цифры, вернитесь в приложение, вставьте в поле кода и нажмите **«Подтвердить вход»**. Не меняйте регистр символов. Это код подтверждения, не OAuth-токен; фиксированную длину кода приложение не требует.
   - Код действует 10 минут.
   - Не закрывайте и не перезапускайте приложение до завершения входа: PKCE-верификатор хранится только в памяти.
   - Если система выгрузила приложение или код истёк, начните вход заново.
6. Нажмите **«Выбрать папку на Диске»**, откройте нужную папку и нажмите **«Использовать эту папку»**. Либо введите путь вручную, например `/Baby Tracker` или `disk:/Baby Tracker`. Нужен путь на вашем Диске, не публичная ссылка. Корень Диска использовать нельзя.
7. Нажмите **«Создать идентификатор дневника»**. Скопируйте полученный UUID для второго телефона.
8. Нажмите **«Подключить общую папку»**, затем **«Синхронизировать»**. Уже имеющиеся локальные события будут включены в обмен.

Приложение создаёт в папке служебный файл `baby-tracker-family.json`. Он связывает папку с идентификатором дневника. Подключение не делает папку публичной и не выдаёт другим людям доступ.

### 4. Подключить второй телефон

Повторите вход и выбор папки под аккаунтом второго родителя. Укажите **тот же идентификатор дневника**, что на первом телефоне. Не генерируйте новый UUID.

Нажмите **«Подключить общую папку»**, затем **«Синхронизировать»**. История первого телефона должна появиться локально. Если во втором телефоне были свои записи, они тоже будут опубликованы; чтобы увидеть их на первом телефоне, выполните обмен на нём ещё раз.

UUID дневника — не пароль и не приглашение в папку. Без разрешения на папку он не даёт доступа. Ошибка «другой идентификатор дневника» означает, что выбрана другая папка или введён другой UUID. Не удаляйте служебный файл, чтобы обойти проверку: возьмите правильный UUID с первого телефона.

## Что синхронизируется

| Данные | Поведение |
| --- | --- |
| События дневника | Объединяются по уникальному ID, без дублей при повторном получении |
| Исправления событий | Передаются как новые версии записи |
| Удаления | Передаются как сохраняемые метки удаления; старая копия события не должна воскреснуть |
| Активный сон | Передаются время начала и параметры; время продолжается на принимающем телефоне |
| Активное кормление грудью | Передаются сторона, пауза и накопленная длительность |
| Профиль малыша | Остаётся локальным; настройте его на обоих телефонах отдельно |
| Пароли, OAuth-сессии и настройки подключения | Не передаются через папку и не входят в JSON-бэкап |

Секундный счётчик таймера по сети не отправляется. Длительность рассчитывается из временных меток. Завершение таймера и соответствующее событие входят в один локальный снимок и один отправляемый пакет.

Если оба телефона изменили **одну и ту же запись или один таймер**, применяется детерминированное правило версий: большая ревизия, затем идентификатор устройства. Это не ручное разрешение конфликтов и не объединение полей одной записи. Включите автоматическую установку времени на обоих телефонах: сильное расхождение часов может повлиять на выбор победившей версии. Разные события сохраняются независимо.

## Состояния и ошибки

- **Есть изменения, ещё не подтверждённые на Диске** — нажмите «Синхронизировать». Изменения другого родителя заранее неизвестны: приложение проверяет папку только по кнопке.
- **Обмен завершён, но появились новые записи** — во время загрузки вы изменили дневник. Нажмите ещё раз, чтобы отправить оставшееся.
- **Нет сети / ошибка сервиса** — локальный дневник остаётся доступным. Повторите обмен после восстановления сети. Автоматического фонового повтора для Диска нет.
- **Истекла или отозвана сессия** — нажмите «Войти в Яндекс заново» и повторите получение кода. Секрет клиента не хранится; автоматическое продление с использованием секрета не выполняется.
- **Нет доступа** — проверьте аккаунт, права «Редактирование», ограничения тарифа и наличие свободного места на Дисках участников.
- **Папка не найдена** — проверьте её путь на этом аккаунте. После переименования или перемещения отключите подключение на этом телефоне и выберите папку заново с прежним UUID.
- **Слишком много запросов / загрузка временно запрещена** — подождите и повторите вручную.
- **Повреждённый пакет или неподдерживаемая версия** — обмен остановится без частичного применения скачанных пакетов. Сохраните резервную копию локального дневника; не редактируйте служебные файлы вслепую.

Ошибки запросов Диска содержат название этапа и диагностический код:

| Код | Этап |
| --- | --- |
| `YD-METADATA` | Проверка выбранной папки |
| `YD-LIST` | Чтение списка файлов и папок |
| `YD-DOWNLOAD-LINK` | Получение ссылки на скачивание файла |
| `YD-DOWNLOAD` | Скачивание файла по выданной ссылке |
| `YD-UPLOAD-LINK` | Получение ссылки на загрузку файла |
| `YD-UPLOAD` | Загрузка файла по выданной ссылке |

Например, `[YD-DOWNLOAD; HTTP 404]` означает, что ответ «не найдено» получен при скачивании файла, а не при проверке пути папки. `HTTP-ответ недоступен` означает, что транспорт не предоставил читаемый ответ; это не позволяет отличить отсутствие сети от CORS/другой блокировки браузером или ошибки транспорта. `ошибка обработки ответа` обозначает некорректный JSON или отсутствующую/недопустимую ссылку передачи.

Для диагностики можно прислать сообщение целиком: приложение не включает в него OAuth-токен, путь папки, подписанную ссылку, тело ответа или исходное исключение транспорта. Ожидаемые `404` при первичной проверке отсутствующего служебного файла и `409` при одновременном создании продолжают обрабатываться автоматически. Коды не доказывают успешную синхронизацию с реальным аккаунтом; для этого нужен отдельный обмен двух устройств.

Ошибка после получения данных, но до отправки или сохранения подтверждения, может оставить уже полученные события локально. Повторный обмен безопасен: применение пакетов идемпотентно, неподтверждённые изменения не считаются отправленными.

## Безопасность, отключение и резервные копии

- В Android сессия сохраняется через защищённый Capacitor-плагин: AES-GCM с ключом Android Keystore. Для iOS используется локальный Keychain без синхронизации токена через iCloud.
- В веб-версии токен хранится **только в памяти вкладки**, а не в `localStorage`, `Preferences` или бэкапе. После перезагрузки нужен новый вход. Браузерные запросы зависят от CORS Яндекса; основной сценарий этой функции — нативное приложение, использующее Capacitor HTTP.
- Кнопка **«Отключить Яндекс Диск на этом телефоне»** выключает обмен и удаляет локальную сессию. Она не удаляет события и файлы в папке, не отключает второй телефон и не отзывает выданное разрешение у Яндекса. Отозвать его можно в настройках доступа [Яндекс ID](https://id.yandex.ru/personal/data-access).
- Неотправленные изменения и журнал версий сохраняются после отключения. При повторном подключении того же дневника они могут быть отправлены.
- Данные пакетов хранятся в JSON **без сквозного шифрования приложения**. Их могут прочитать участники с доступом к папке; это не защищённый от провайдера медицинский архив.
- JSON-экспорт в разделе «Резервная копия» предназначен для отдельного резервирования. Его импорт **полностью заменяет локальную историю**, а не объединяет её. При подключённом Диске замена попадёт в следующий ручной обмен, включая удаления старых записей. Отключение само по себе не делает восстановление навсегда локальным: после повторного подключения того же дневника изменения тоже могут распространиться.
- Не переключайте регулярно один дневник между Supabase и Диском. При переходе завершите обмен на обоих телефонах, сохраните бэкапы и выберите один способ на обоих устройствах. Ревизии удалений не мигрируют между разными областями синхронизации.

## Как устроен файловый обмен

В выбранной папке находятся:

```text
baby-tracker-family.json
baby-tracker-<UUID дневника>-<UUID пакета>.json
baby-tracker-<UUID дневника>-<другой UUID пакета>.json
```

Пакет содержит полный снимок журнала событий и таймеров с версиями и метками удалений. При наличии изменений создаётся **новый файл с уникальным именем**, без перезаписи старого. Телефоны не конкурируют за один `history.json`. Новые пакеты проверяются целиком и объединяются одной локальной записью; уже обработанные имена сохраняются отдельно.

**Служебные файлы не редактируйте и не удаляйте вручную.** Автоматической очистки старых пакетов пока нет: число файлов и занимаемое место растут с количеством обменов, публикующих изменившийся журнал. Повторный обмен без новых данных не создаёт очередной пакет. Удаление события из дневника не удаляет его старые версии из файлов Диска — для полного удаления облачной истории потребуется отдельно удалить архивную папку и прекратить её использование на всех телефонах.

При обычном обмене отсутствующий файл идентификации не создаётся заново: приложение сообщает об ошибке. Если папка была намеренно создана заново, явное повторное подключение проверяет её и сбрасывает старое подтверждение публикации, чтобы локальная история была отправлена в новую папку.

## Запуск и сборка проекта

Требуются Node.js 22+, npm и, для Android, настроенные Android SDK/JDK для Capacitor 8. Версии зависимостей закреплены в `package-lock.json`.

```bash
npm ci
npm start
```

Веб-приложение по умолчанию доступно на `http://localhost:4200`.

Проверки выполняются последовательно:

```bash
npx tsc --noEmit
npm run build
npx ng test --watch=false
```

Обновление нативного Android-проекта после сборки:

```bash
npx cap sync android
npx cap open android
```

Соберите и установите приложение из Android Studio. Плагины `@capacitor/browser` и `@aparajita/capacitor-secure-storage` подключаются через Capacitor; сгенерированные нативные файлы вручную править не нужно. Для iOS необходим отдельно созданный и настроенный нативный проект; наличие iOS-ветки в плагинах не означает проверенную сборку iOS этого репозитория.

В установленном Ionic 9.0.8 standalone-компоненты экспортируются из `@ionic/angular`; старый подпуть `@ionic/angular/standalone` отсутствует в экспортах этой версии.

### Геометрия вкладок и нижняя безопасная область

Корневые компоненты страниц внутри `ion-router-outlet` сохраняют стандартный flex-контейнер Ionic `.ion-page`. Не задавайте им `display: contents`: заголовок перестаёт участвовать в расчёте высоты страницы, и область прокрутки выходит под нижнюю панель вкладок. Исправление применяется к настройкам, статистике и скачкам развития; дополнительные отступы на высоту панели не нужны. Нижнюю безопасную область учитывает сам `ion-tab-bar`, а панель быстрых действий «Сегодня» остаётся в `ion-footer` над вкладками.

Проверка исправления: локальный интерфейс в Chromium и WebKit с iPhone user agent; все четыре вкладки, портретный и альбомный экраны, ширина 320 px, уменьшенная высота окна и имитация `--ion-safe-area-bottom` 21/34 px. Проверены прокрутка до конца, отсутствие перекрытия нижнего содержимого, доступность кнопки сохранения настроек и открытие формы измерений из статистики. Это браузерная проверка, не проверка APK, физического iPhone, установленной PWA или настоящей экранной клавиатуры.


## Android APK и релизы

GitHub Actions (`.github/workflows/android-release.yml`) проверяет TypeScript, собирает production-веб-приложение, запускает тесты и собирает unsigned release APK при push в `main`, pull request и ручном запуске. Неподписанный APK сохраняется как диагностический артефакт на 7 дней; установить его нельзя.

CI использует JDK 21, Android SDK 36 и явный пакет `platform-tools` вместо удалённого SDK-пакета `tools`. Тестовые файлы запускаются с `isolate: true`, чтобы mocks Capacitor в проверках синхронизации и OAuth не влияли друг на друга.

Push тега `v*` дополнительно подписывает APK постоянным release-ключом, проверяет подпись и выравнивание и публикует `lulio-baby-tracker-v<версия>.apk` и `SHA256SUMS` в GitHub Releases. Релиз сначала создаётся черновиком и становится опубликованным только после загрузки обоих файлов. В приватном репозитории скачать его могут только пользователи с доступом.

### Однократная настройка подписи

Владелец самостоятельно создаёт ключ вне репозитория (если приложение уже распространялось, нужен **тот же ключ**, а не новый):

```bash
keytool -genkeypair -v -keystore "$HOME/baby-tracker-release.jks" \
  -alias baby-tracker -keyalg RSA -keysize 3072 -validity 10000
```

Пароли вводятся интерактивно. Не коммитьте ключ, пароли или их base64-представление; храните резервную копию ключа и паролей вне репозитория. Потеря ключа лишает возможности обновлять уже установленное приложение.

В Settings → Secrets and variables → Actions создайте repository secrets:

| Secret | Значение |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | Содержимое release-keystore в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | Пароль keystore |
| `ANDROID_KEY_ALIAS` | Alias ключа, например `baby-tracker` |
| `ANDROID_KEY_PASSWORD` | Пароль ключа (для PKCS12 обычно совпадает с паролем keystore) |

На macOS ключ можно передать напрямую в GitHub CLI, не выводя его в терминал:

```bash
base64 -i "$HOME/baby-tracker-release.jks" | gh secret set ANDROID_KEYSTORE_BASE64
gh secret set ANDROID_KEYSTORE_PASSWORD
gh secret set ANDROID_KEY_ALIAS
gh secret set ANDROID_KEY_PASSWORD
```

### Выпуск версии

Источник версии — `package.json`; обновите также корневые версии в `package-lock.json`. Тег должен точно совпадать с `v<версия>`, например `v1.0.0`. Скрипт `scripts/android-version.gradle` задаёт `versionName` и `versionCode`, не изменяя сгенерированные Android-файлы. Формула кода — `major × 1000000 + minor × 1000 + patch` (`1.0.0` → `1000000`); minor и patch не превышают 999, код не превышает 2100000000. Для обновлений всегда повышайте версию.

Тот же Gradle init-скрипт подключает ресурсный overlay `scripts/android-res`, задающий имя Android-приложения **Lulio** и заголовок **Lulio: baby tracker**, без ручных изменений в `android/`. Для локальной сборки с релизным именем запускайте из `android/`: `bash ./gradlew --init-script ../scripts/android-version.gradle assembleDebug`.

После успешной CI-проверки `main` и настройки четырёх секретов:

```bash
git tag -a v1.1.0 -m "Lulio: baby tracker v1.1.0"
git push origin v1.1.0
```

Следите за workflow **Android APK** во вкладке Actions. Если выпуск прервался, исправьте причину и перезапустите неуспешные jobs; публикация допускает повторный запуск. Готовые APK доступны во вкладке Releases. Android потребует разрешить установку из выбранного источника; Google Play для этого не нужен.

## Проверка реализации

Автоматические тесты охватывают обмен двух локальных устройств, исправления и удаления, передачу активного сна, повторную обработку, перезапуск с неотправленными данными, ошибку загрузки, запись во время отправки, повреждённый пакет, чужой UUID, восстановление папки и защиту OAuth-сессии.

Браузерный smoke-прогон выполнялся в запущенном приложении с локально подменёнными ответами OAuth и Диска: проверены PKCE, получение события, сбой и повтор отправки, публикация удаления и отсутствие тестового токена в `localStorage`. Это **не проверка реальных аккаунтов Яндекса**.

После регистрации своего OAuth-приложения проверьте на двух настоящих телефонах:

1. Оба родителя независимо входят в Яндекс и подключают одну папку с одинаковым UUID.
2. Событие с первого телефона появляется на втором после последовательного обмена.
3. Исправление, удаление и незавершённый таймер передаются в обе стороны.
4. Без сети запись сохраняется, а после восстановления сети отправляется по кнопке.
5. После перезапуска нативного приложения вход сохраняется, а неотправленные события не теряются.
